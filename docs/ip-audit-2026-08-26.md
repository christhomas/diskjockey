# IP & Licence Audit — 2026-08-26

Scope: every Rust crate the app links, the Go network-filesystem drivers, and the
first-party source of all of them. Resolved from the dependency graphs rather than from
the previous audits, which is how the stale entries below were found.

**This document is internal.** It names GPL-licensed tools directly, which the public
vendor repositories must not do.

## Verdict

✅ **No copyleft anywhere in the shipped binary, and no known vulnerability in it.**

Both were true only after this audit found them. The audit is dated by when it was
started; the two findings below were fixed the same day, and this records the end state
with the route to it, because "we removed it" is the useful fact and "we had it" is the
one that explains why the removal was not obvious.

⚠️ **Two compliance documents are materially out of date**, in the direction that
understates what is shipped. See *Findings*.

## What is actually linked

Ten Rust crates, statically, through the per-extension bundles in `rust-bundles/`.
None of them is a submodule any more — they come from crates.io:

| Crate | Licence |
|---|---|
| `am-fs-core`, `am-fs-ext4`, `am-fs-xfs`, `am-fs-btrfs`, `am-fs-erofs`, `am-fs-squashfs` | MIT |
| `am-fs-ntfs` | MIT OR Apache-2.0 |
| `am-img-qcow2`, `am-img-vhd`, `am-img-vhdx`, `am-img-vmdk` | MIT |
| `am-lzo1x`, `am-partitions` | MIT |

Their transitive closures were resolved with `cargo metadata` and are entirely MIT,
Apache-2.0, BSD, Zlib, ISC, 0BSD, CC0-1.0, MIT-0 or Unicode-3.0. **No copyleft in any
Rust dependency tree.**

Plus `go-networkfs`, built by `make all` into `lib/go-networkfs` and referenced by the
Xcode project — so it ships.

## Copyleft: none, and how it left

There was exactly one piece, and it arrived through the FTP driver:

```
go-networkfs/ftp → github.com/jlaffaye/ftp (ISC) → hashicorp/go-multierror (MPL-2.0)
                                                 → hashicorp/errwrap (MPL-2.0)
```

Two error-aggregation helpers doing work the standard library has done since Go 1.20,
pulled in transitively by an FTP client library.

MPL-2.0 is **file-scope** weak copyleft, so this was compliant — the obligation attaches
to modifications of those files, not to a work that links them. It was still the only
copyleft in the project, and it was removable.

The FTP driver now uses `antimatter-studios/goftp`, a fork of `secsy/goftp` which
depends on **nothing outside the standard library** — verified from its imports rather
than from a generated manifest. The obvious alternatives were worse: the library we had
carried the MPL, and the maintained SMB fork (below) carried it too.

```
$ go list -deps ./... | grep -c hashicorp
0
```

## The SMB vulnerability, and why the obvious fix was wrong

Not a licensing finding, but it turned on the same evidence and is recorded here because
the two were nearly traded against each other.

**GO-2026-5051** — an out-of-bounds read and panic in `ReadDir` in
`hirochachacha/go-smb2`, reachable from the SMB driver. A directory listing against a
hostile or man-in-the-middle server crashes the process. The advisory records
`Fixed in: N/A`; that library was last released in 2021.

The maintained fork, `cloudsoda/go-smb2`, carries the fix. Taking it would have been a
mistake:

| | before | switching to cloudsoda |
|---|---|---|
| reachable vulnerabilities | 1 | **5** (gokrb5) |
| copyleft in the compiled set | none | **MPL-2.0** again, via gokrb5 |

So the fix was backported onto a fork of the *original* instead —
`antimatter-studios/go-smb2` — which is upstream plus the security hunks and nothing
else. Credit for the fix is Arash Payan's at cloudsoda; both repositories are
BSD-2-Clause.

```
$ govulncheck ./...
No vulnerabilities found.
```

## The two forks, and what they commit us to

| fork | of | why | contains |
|---|---|---|---|
| `antimatter-studios/goftp` | `secsy/goftp` | a dial hook we needed; upstream idle | 12 issue fixes + containerised tests |
| `antimatter-studios/go-smb2` | `hirochachacha/go-smb2` | a security fix upstream will not make | the bounds checks |

Both are **MIT** and **BSD-2-Clause** respectively, unchanged from their upstreams, and
both track upstream exactly with our changes as pull requests on top — 13 offered to
`secsy/goftp`, 1 to `hirochachacha/go-smb2`. If those land, each fork reduces to a
single commit renaming the module path.

That module path matters for this document's purpose: without it, a licence audit and
`go mod why` both name the upstream for code that is ours, and a vulnerability scanner
matching by module path would report our SMB fork as still carrying GO-2026-5051.

## Two false positives this audit produced, recorded so the next one does not repeat them

Both came from matching licence text by substring, and both looked like findings.

**`r-efi`** is declared `MIT OR Apache-2.0 OR LGPL-2.1-or-later`. A search for `GPL`
matches it. It is not a finding for three independent reasons: the licence is
*disjunctive*, so MIT applies; it is a dev-dependency only
(`tempfile` → `getrandom` → `r-efi`); and it is gated to UEFI targets, so it is absent
from the normal dependency graph entirely.

**`hashicorp/errwrap` and `hashicorp/go-multierror`** first classified as **AGPL**. They
are MPL-2.0. The MPL's own text names the GNU GPL, LGPL and AGPL in its "Secondary
License" definition, so a classifier that tests for GNU licences before testing for the
MPL reports every MPL file as GNU-licensed.

The lesson generalises: **test for MPL-2.0 before testing for any GNU licence**, and
treat a disjunctive licence as satisfied by its most permissive term.

## Provenance of the format knowledge

- **No vendored C or C++** anywhere in the crates.
- **No file cites a GPL implementation as its origin.** Every match for "derived from",
  "ported from" or "based on" is either ordinary English about a value derived from
  another value, or an explicit disclaimer — `rust-fs-erofs` states outright in three
  places that it is *not* derived from the GPL-2 kernel encoder or from `erofs-utils`.
- **The reference tooling is executed, never read as source.** New this cycle:
  `rust-fs-xfs` builds the stress generators from the filesystem test suite inside the
  oracle VM. Its source and build tree exist only in the guest, nothing from it enters
  the repository, and the binaries are invoked as external programs. Both
  `tests/vagrant/debian/provision-stress-tools.sh` and
  `scripts/vm-build-stress-fixtures.sh` carry that reasoning where someone changing them
  will read it.
- The corroboration habit noted in the 2026-08-25 audit continues, and did real work
  this cycle: the XFS inode-cluster rule was confirmed against 7,307 log items across
  four allocation groups and four geometries rather than asserted once.

## Findings

### 1. `THIRD_PARTY_LICENSES.md` was materially incomplete — **fixed here**

It listed four components. The shipped binary statically links **thirteen** Rust crates;
six were absent, including four whole filesystems, along with `am-fs-core`, `am-lzo1x`
and `am-partitions`.

Every one is MIT, so nothing was unlicensed — but a notice file that omits most of what
it is a notice for does not discharge the obligation it exists for.

It also attributed the MPL-2.0 modules to the **SMB** driver. They came in through
**FTP**. Both are now moot, since neither ships, but the file records the two forks in
their place.

### 2. `IP_SWEEP_REPORT.md` described a project that no longer matched — **fixed here**

Dated 2026-05-03. Since then six filesystem crates were added and are absent from it;
the crates moved from submodules to crates.io; the Swift Package Manager dependency it
records is no longer present at all; and the Go closure it puts at **44 modules** was
**117**.

That last one mattered most, because Go was where the only copyleft lived. It is now a
pointer to this audit.

### 3. `vendor/rust-disk-probe` is committed in-tree, unpinned — **open**

First-party and MIT, so no licence question. But unlike every other entry in `vendor/`
it is not a submodule, is absent from `.gitmodules`, and is absent from
`VENDOR_PINS.txt` — so the one place recording what version of each dependency is in use
does not record it. A reproducibility gap that reads as a provenance gap.

### 4. Go closure coverage was partial — **open**

Of the modules in the graph, only those present in the local module cache had a licence
file to read. The classified set held no surprises and contained the MPL entries that
have since been removed, but the remainder is a gap in the method rather than a finding
about the project.

Closing it needs the cache populated (`go mod download`) and a re-run.

### 5. A naming nit in first-party source — **open**

`rust-fs-ext4/src/mkfs.rs` names `e2fsprogs` in three comments describing a convention
the driver matches behaviourally. It is the only occurrence of a reference tool's name
in any shipped source across all thirteen crates. No derivation is claimed and it is no
licence risk; it is only inconsistent with the policy that vendor repositories refer to
tools by role. Worth rewording next time that file is touched.

## Two things worth carrying to the next audit

**Test for MPL-2.0 before any GNU licence.** The MPL's own text names the GNU GPL, LGPL
and AGPL in its "Secondary License" definition, so a classifier checking for GNU first
reports every MPL file as GNU-licensed. This audit did exactly that and briefly believed
the project contained AGPL code.

**Treat a disjunctive licence as satisfied by its most permissive term.** `r-efi`
declares `MIT OR Apache-2.0 OR LGPL-2.1-or-later` and matches a search for `GPL`. It is
not a finding: the licence is disjunctive, it is a dev-dependency only, and it is gated
to UEFI targets so it never builds here.
